## How the deployed image was built

The build re-ran the [v229 recipe](../v16-prod-229/README.md) on the v229 image
itself. Its Dockerfile differs from v229's `context/Dockerfile` only in the
base digest, the tool directory (`/tmp/upgrade-230`), the absence of the
dependency-wheel step (the dependency delta is empty) and the labels. Apart
from the two custom applications and the tool records that name their new pins
and the empty dependency delta, every input was byte-identical to v229's build
context: the six pinned upstream archives with the same 49 source overlays, the
retained Insights, Print Designer and Telephony files, the patchers, the Python
locks and the dependency bundle.

The build therefore re-copied the Frappe, ERPNext, HRMS, CRM, Helpdesk and
Drive trees unchanged, re-verified the overlays, reinstalled eight editable
applications (those six plus EAM and `my_branding`) without a package index,
re-ran the frozen-lockfile frontend installs, re-ran and verified the
installed-dependency patcher and the security-patch check, and rebuilt the
frontend assets of those eight applications. As for v229, the stacked image
was then flattened into one layer with its configuration restated (441,533
entries, the same filesystem as the stacked build).

## What changed, compared file by file

The v229 and v230 images were compared read-only: every regular file by
SHA-256, permission and owner, every symlink target and every directory; only
`__pycache__` directories were left out. The ten application trees that matter
here, all seven AGPLv3 applications (CRM, Drive, Gameplan, Helpdesk, Insights,
Print Designer, Telephony) and the six upstream trees the build re-copied
(Frappe, ERPNext, HRMS, CRM, Helpdesk, Drive), hold 328,837 files, 4,000
symlinks and 38,352 directories in each image.

No source file differs. Gameplan, Helpdesk, Insights, Print Designer and
Telephony are byte-identical, including their built assets. The 108 paths that
differ were all generated by the rebuild:

- 26 Frappe, ERPNext and HRMS CSS bundles carry new hashed names. Their CSS is
  identical apart from the `sourceMappingURL` line; each source map records the
  temporary build directory, and that path feeds the hash in the file name.
- Two CRM source maps: `sw.js.map` records the temporary build directory, and
  `demoData-CFNi97zr.js.map` lists bundler asset placeholders in a different
  order. The JavaScript they describe is identical.
- Two Drive package-manager state files under `frontend/node_modules`
  (timestamps and store path).

Outside the application trees, only `assets/assets.json` and
`assets/assets-rtl.json` (the renamed bundles), the editable-install metadata
timestamps of the eight reinstalled applications and the new `/tmp/upgrade-230`
tool directory differ.

The AGPL-covered sources and every published modification are therefore
[v229's](../v16-prod-229/README.md), unchanged. Follow the v229 recipe and its
inherited manifests for their sources and build instructions.

## Reproducing the changed layer

`my_branding` is the published runtime application in this mirror, at the
commit above. EAM is MIT-licensed and maintained in a private repository. It is
not part of the AGPL Corresponding Source offer, and a public reader cannot
rebuild its layer from this mirror.

The `Dockerfile` here is an app-only reproduction, not the file that built the
deployed image. On the exact v229 image it replaces only `apps/eam` and
`apps/my_branding`, reinstalls those two applications, rebuilds only their
frontend assets and re-verifies the retained overlays and dependency locks with
the v229 tools already in the base. The other applications keep v229's built
assets, which differ from the deployed image only in the generated files listed
above. This Dockerfile was test-built offline for `linux/amd64` on 22 November
2026, from the `prepare.py` output on the exact v229 image, and every step
passed. In the result, `apps/eam`, `apps/my_branding` and their built assets
(`assets/eam`, `assets/my_branding`) are identical to the deployed image, file
by file, including permissions.

With both repositories, run `python3 prepare.py --branding PATH --eam PATH` and
build this directory for `linux/amd64`. The helper validates the immutable
base, each commit and Git tree, the image labels and the app layout before
writing anything, then extracts the exact pinned commits (`my_branding` without
`docs/` and `ops/`, as in the deployed build context). Its output was compared
with the context that built the deployed image: 759 `my_branding` and 874 EAM
entries, identical byte for byte and mode for mode. Generated archives are
ignored by Git.
